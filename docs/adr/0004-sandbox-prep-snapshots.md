# ADR-0004. 샌드박스 준비 시간을 스냅샷으로 줄일지 (초안)

- 상태: 초안 (사용자 결정 대기. 스냅샷 생성·저장 코드는 아직 없다)
- 날짜: 2026-09-19
- 관련: `packages/sandbox/live.ts`, `packages/sandbox/run.ts`, `packages/sandbox/toolkit.ts`, `apps/web/src/lib/notifications/test-run-queue.ts`
- 이어받는 결정: [ADR-0001](./0001-test-runtime.md) (Vercel Sandbox), [ADR-0002](./0002-run-sandbox-from-web.md) (web 이 샌드박스를 부른다, 팀 단위 직렬), [ADR-0003](./0003-dante-provided-test-toolkit.md) (Dante 도구 세트)

## 배경

실행 한 번은 매번 빈 샌드박스에서 시작한다. `Sandbox.create({ source: git })` 로 클론하고, 레포 install 을 하고, 라이브 실행(`runTestLive`)은 Dante 도구(`toolkit.ts`)를 npm 으로 또 설치한다. PR 실행(`runTest`)에는 도구 단계가 없다.

- 라이브 실행은 대기열이 없다. 준비 시간이 그대로 사용자가 터미널 앞에서 기다리는 시간이다.
- PR 실행은 팀 단위 직렬(`test-run-queue.ts`)이다. 준비 시간이 그대로 같은 팀의 다음 실행이 기다리는 시간이 된다.

## 측정 (2026-09-19, `wlrnjs/dante-vitest-sample`, vcpus 2, iad1)

샘플 레포는 npm(`npm ci`), React 18, 의존성 7개다. 테스트 파일 1개(4개 중 1개 일부러 실패). 같은 시간대에 다른 세션도 같은 샘플 프로젝트로 샌드박스를 돌렸을 수 있어 값이 1~3초 흔들린다.

### 단계별 (라이브 실행, 각 3회 평균, ms)

| 단계                                     | 변경 전 | 변경 후 (이 브랜치) |
| ---------------------------------------- | ------: | ------------------: |
| setup (create + 클론 + 테스트 파일 쓰기) |   1,896 |               1,660 |
| install (레포 `npm ci`)                  |   3,216 |               3,578 |
| toolkit (도구 설치, 변경 후는 추가 대기) |  11,916 |               9,064 |
| test                                     |   1,728 |               1,924 |
| 그 밖(리포트 읽기 + `stop`)              |   6,645 |               3,490 |
| 합계                                     |  25,401 |              19,716 |

### 개별 실험

| 실험                                           | 결과                                                    |
| ---------------------------------------------- | ------------------------------------------------------- |
| 소스 없이 create / 직접 `git clone --depth 1`  | 0.97초 / 0.97초                                         |
| git 소스로 create (클론 포함)                  | 1.17초                                                  |
| 기존 스냅샷에서 create                         | 0.62~0.88초 (도구·레포 `node_modules` 가 그대로 있음)   |
| 레포 install 과 도구 설치를 동시에 (3회)       | 벽시계 11.6~13.2초. 순차면 install 약 3초가 더해진다    |
| 도구 설치, 빈 캐시 + `--prefer-offline`        | 10.4~13.7초. 효과 없음(새 샌드박스의 `~/.npm` 은 4KB)   |
| 도구 설치, 캐시가 찬 상태 + `--prefer-offline` | 3.5~4.0초 (새 샌드박스에서는 이 상태가 안 생긴다)       |
| 도구 설치, lockfile 을 미리 넣고 `npm ci`      | **2.1초** (같은 샌드박스 조건에서 lockfile 없이 11.4초) |
| `stop()`, 기본값(persistent)                   | 4.4초, 매번 약 0.79GB 자동 스냅샷을 만든다              |
| `stop()`, `persistent: false`                  | 1.5~2.5초, 스냅샷 없음                                  |

샌드박스 이미지: node 24.21.0, npm 11.19.0, vCPU 2.

### 해석

1. 도구 설치의 대부분은 다운로드가 아니라 **의존성 해석**(패키지마다 레지스트리 메타데이터 조회)이다. lockfile 이 있으면 11초가 2초가 된다.
2. 클론·create 는 합쳐 1~2초라 줄일 여지가 작다.
3. 샘플 레포 install 은 3초다. 레포 install 스냅샷의 이득은 레포가 클 때만 크다. 실제 사용자 레포로 다시 재야 한다.
4. SDK 3 의 `Sandbox.create` 는 **기본이 persistent** 라 `stop()` 때마다 스냅샷을 만든다. 우리는 이걸 의도한 적이 없다. 2026-09-19 기준 프로젝트에 자동 스냅샷 67개, 64.4GB 가 쌓여 있다(가장 오래된 것 9-14). 각각 마지막 사용 후 30일 보관이고 저장 요금이 붙는다.

## 이 브랜치에서 한 것 (스냅샷 없이 코드만)

- 라이브 실행: 레포 install 과 도구 설치를 동시에 돌린다. 도구는 `/tmp/dante-toolkit` 에 따로 설치해 디렉터리·lockfile 이 겹치지 않는다. npm 캐시(`~/.npm`)는 같이 쓰지만 npm 캐시는 동시 접근을 견딘다. 화면 단계와 저장 로그 순서는 예전과 같다(도구 출력은 install 이 끝난 뒤 흘린다). install 이 실패하면 도구 설치를 멈추고 예전과 같은 에러로 끝난다.
- 라이브 실행: `persistent: false`. 자동 스냅샷을 만들지 않고 `stop()` 이 빨라진다.
- PR 실행(`run.ts`)은 건드리지 않았다. 대기열·락 동작도 그대로다.

## 선택지

### A. 도구 lockfile 고정 (스냅샷 없음)

`toolkit.ts` 의 러너별 도구 세트마다 `package.json`·`package-lock.json` 을 코드에 두고, 샌드박스에 써 넣은 뒤 `npm ci` 한다.

- 도구 설치 11초 → 2초. 이 브랜치 적용 후 기준으로 install(3초)과 동시에 돌면 도구 대기는 거의 0 이 된다
- 스냅샷·DB·Vercel 권한이 필요 없다
- 도구의 하위 의존성까지 고정된다. ADR-0003 의 "실행마다 최신을 받지 않는다" 와 같은 방향이다
- lockfile(vitest 약 67KB, jest 비슷한 규모)을 커밋하고, 도구 버전을 바꿀 때 다시 만들어야 한다. 로컬 npm 10.9.2 는 이 조합에서 lockfile 생성이 실패했다(`edgesOut` 오류). 샌드박스(npm 11)에서 만드는 절차가 필요하다
- 도구 세트와 lockfile 이 어긋나면 테스트로 잡게 한다

### B. 도구 기본 스냅샷

빈 샌드박스에 도구 세트를 설치하고 스냅샷을 떠 둔다. 실행은 `source: { type: "snapshot" }` 으로 만들고 레포는 명령으로 클론한다(스냅샷 소스와 git 소스는 같이 쓸 수 없다).

| 항목      | 안                                                                                                                                                                                     |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 누가·언제 | 도구 세트가 바뀔 때 한 번. 배포 후 스크립트, 또는 첫 실행이 없으면 만든다(lazy). lazy 는 동시에 여러 개가 만들어질 수 있어 한 곳에서만 만들게 해야 한다                                |
| 키        | `TOOLKIT_PACKAGES[framework]` 의 해시. 도구를 바꾸면 키가 바뀌어 새로 만든다                                                                                                           |
| 만료·비용 | 기본 30일, 쓰면 타이머가 다시 시작된다. `0` 이면 무기한. 크기는 이미지 포함 1GB 안팎(측정한 자동 스냅샷 0.79~0.88GB). $0.08/GB-월이라 러너 2개면 월 $0.2 이하                          |
| 저장 위치 | (1) 코드 상수·env: 단순하지만 바꿀 때마다 배포 (2) DB 테이블 `sandbox_snapshots(kind, key, snapshot_id, region, created_at, expires_at)`: lazy 생성·무효화에 필요. 마이그레이션이 있다 |
| 무효화    | 키가 바뀌면 옛 것은 안 쓴다. 쓰지 않으면 30일 뒤 사라진다. 만료·삭제된 스냅샷으로 만들면 실패하므로 그때 git 소스 경로로 떨어지고 다시 만든다                                          |
| region    | 스냅샷은 만든 region 에서만 쓴다. 지금 샌드박스는 기본 iad1 이다. region 을 코드에 고정할지 정해야 한다                                                                                |
| 이득      | A 를 하면 추가 이득은 도구 설치 2초 + create 약 0.5초. A 없이 B 만 하면 11초                                                                                                           |

### C. 레포 install 스냅샷 (프로젝트 × lockfile 해시)

실행이 성공하면 레포 install(와 도구)이 끝난 상태를 스냅샷으로 떠 두고, 다음 실행은 그 스냅샷에서 `git fetch` + checkout 만 한다. lockfile 이 같으면 install 을 건너뛴다.

| 항목      | 안                                                                                                                                                                                                                                             |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 누가·언제 | 성공한 실행이 끝날 때(`stop` 대신 `snapshot()`). 첫 실행은 이득이 없다. 스냅샷을 뜨는 시간(측정한 stop 4.4초 수준)이 그 실행 뒤에 붙는다 — 라이브 실행은 결과를 먼저 보내고 뒤에서 떠야 한다. PR 실행은 팀 락을 잡은 채로 뜨면 대기가 늘어난다 |
| 키        | 프로젝트 + lockfile 해시. 샌드박스를 만들기 전에 알아야 하므로 GitHub API 트리의 lockfile blob SHA 를 쓴다(클론 전에 조회 1회)                                                                                                                 |
| 만료·비용 | 프로젝트마다 1개만 둔다(새로 뜨면 옛 것 삭제). 크기는 레포·`node_modules` 에 비례. 큰 모노레포는 수 GB 가 된다. 프로젝트 100개 × 2GB 면 월 $16                                                                                                 |
| 저장 위치 | DB 테이블이 필요하다(프로젝트별·키별). 프로젝트 연결 해제·삭제 때 같이 지운다                                                                                                                                                                  |
| 무효화    | lockfile SHA, install 커맨드, 도구 세트 해시 중 하나라도 바뀌면 새로 만든다. 레포 push 로 소스만 바뀐 경우는 fetch 로 따라간다                                                                                                                 |
| 보안      | 스냅샷에 private 레포 소스와 `node_modules`(postinstall 결과 포함)가 들어간다. 다른 프로젝트·팀과 절대 섞이면 안 된다. 리포트 파일 등 지난 실행의 잔여물(`/tmp/dante-report.json`)을 실행 전에 지워야 한다                                     |
| 이득      | 레포 install 시간 전부. 샘플 레포는 3초라 작다. 실제 사용자 레포로 재 봐야 판단할 수 있다                                                                                                                                                      |

### D. 도구를 넣은 커스텀 이미지 (VCR)

`Sandbox.create({ image })` 로 도구가 깔린 이미지를 쓴다. 만료가 없고 git 소스와 같이 쓸 수 있다. 이미지를 Vercel Container Registry 에 올리는 빌드·권한이 필요하다. 측정하지 않았다.

### Vercel 권한

- 지금 샌드박스 호출은 팀 오너가 발급한 팀 범위 토큰(`VERCEL_TOKEN`) 또는 배포 환경 OIDC 로 한다. 이 토큰으로 샌드박스 생성, 스냅샷 목록 조회, 기존 스냅샷에서 생성까지는 이번 측정에서 됐다. 같은 API 의 `snapshot()` 도 될 것으로 보이지만 명시적으로 확인하지 않았다(자동 스냅샷은 이 토큰으로 이미 만들어지고 있다).
- 사용자(팀 뷰어)가 직접 못 하는 것: 대시보드에서 스냅샷 삭제, 사용량·Spend Management 알림 설정, 커스텀 이미지(D) 푸시. 오너가 해야 한다.

## 사용자가 결정할 것

1. PR 실행(`run.ts`)에도 `persistent: false` 를 넣을지. 넣으면 PR 실행마다 약 2~3초 빨라지고(팀 대기도 그만큼) 자동 스냅샷이 더 쌓이지 않는다. PR 경로 담당·04 배치와 겹치지 않게 누가 할지.
2. 이미 쌓인 자동 스냅샷(67개, 64.4GB, 같은 날 10:40 이후 생긴 16개 13.7GB 는 대부분 이번 측정이 만든 것)을 지울지. 지우면 되돌릴 수 없다. 오너가 대시보드나 CLI(`sandbox snapshots delete`)로 한다.
3. A(도구 lockfile 고정)를 할지. 스냅샷 없이 라이브 실행이 약 9초 더 빨라진다. 한다면 lockfile 을 어디서(샌드박스 npm 11) 누가 다시 만드는지.
4. B(도구 기본 스냅샷)를 할지. A 를 하면 이득이 2~3초로 줄어든다.
5. C(레포 install 스냅샷)를 할지, 하기 전에 어떤 실제 레포로 install 시간을 재 볼지.
6. B·C 를 한다면 스냅샷 ID 를 어디에 둘지(코드·env 상수 / DB 테이블 + 마이그레이션).
7. 만료 정책: 기본 30일(사용 시 연장) / 짧게 / 무기한.
8. 스냅샷을 누가 만드는지: 배포 후 스크립트(오너 토큰) / 첫 실행 lazy / 수동.
9. region 을 iad1 로 고정할지.
10. 스냅샷 저장 요금 알림·상한(Spend Management)을 오너가 걸지.
11. 단계 시간 로그를 서버 로그로 상시 남길지. 지금은 단계 이벤트(`ms`)가 화면으로만 가고 서버에는 남지 않는다. 이번 측정은 임시 스크립트로 했다.

## 뒤집을 수 있는가

이 브랜치의 두 변경(동시 설치, `persistent: false`)은 `live.ts` 안에서 끝나 되돌리기 쉽다. B·C 는 DB 테이블과 외부 상태(스냅샷)가 생기므로 되돌릴 때 스냅샷 정리가 따라온다.
